# تصميم: نموذج الصلاحيات الرباعي (RBAC v2) وإحكام موثوقية المزامنة

**التاريخ:** 2026-09-02
**النطاق:** إضافة دور «إداري» رابع بين مدير النظام ومُدخل البيانات وفق مبدأ فصل الواجبات، وجعل سجل التدقيق غير قابل للمحو، وحماية آخر حساب مدير، وإظهار فشل المزامنة بدل ابتلاعه صامتاً.
**يبني على:** `2026-09-01-firebase-auth-security-hardening-design.md`

---

## 1. الدافع

نموذج الأدوار الحالي ثلاثي (`admin` / `operator` / `viewer`) ويجمع في `admin` ثلاث سلطات تفصلها الأنظمة المؤسسية عادةً: إدارة الهويات، والتعافي من الكوارث، وتعديل البيانات. النتيجة أن كل من يحتاج صلاحية تعديل واسعة على البيانات يُمنح معها القدرة على مسح قاعدة البيانات واستعادة لقطة قديمة وفتح أدوات المطوّر.

المطلوب دور يملك **البيانات كاملة** دون أن يملك **الهوية ولا التعافي ولا التدمير**.

وأثناء تصميم ذلك ظهرت ثلاث ثغرات موثوقية في نفس نطاق العمل، معالجتها جزء من هذه الوثيقة لأنها تمسّ المسارات ذاتها.

---

## 2. مبدأ التصميم: فصل الواجبات (Separation of Duties)

القاعدة المعتمدة، وهي معيار متبع في SAP و Workday و Oracle HCM و ServiceNow:

> من يدير الهويات لا يدير البيانات، ومن يدير البيانات لا يملك أدوات التعافي والتدمير.

يترتب على ذلك أن السلطات الأربع التالية تبقى حكراً على `admin` دون سواه:

1. إدارة الحسابات وإسناد الأدوار.
2. استعادة لقطة أرشيفية كقاعدة بيانات حية.
3. تنفيذ حذف قاعدة البيانات الشامل.
4. فتح أدوات المطوّر (F12).

---

## 3. نموذج الأدوار

| المفتاح | المسمّى | ما يقابله مؤسسياً | جوهر الدور |
| :--- | :--- | :--- | :--- |
| `admin` | مدير النظام 👑 | System / Security Administrator | الهوية والتعافي والتدمير، إضافةً لكل صلاحيات الإداري |
| `manager` | إداري 🛡️ | HR Functional Administrator | سلطة كاملة على البيانات، بلا هوية ولا تعافٍ ولا F12 |
| `operator` | مُدخل بيانات ✍️ | Data Entry Clerk | تبويبات محدّدة يمنحها له المدير |
| `viewer` | مستعرض 👁️ | Read-only / Auditor | اطلاع وبحث وطباعة وتصدير فقط |

**تغيير تسمية:** `operator` كان يُعرض باسم «إداري مُدخل»، ويصبح «مُدخل بيانات» لإزالة اللبس مع الدور الجديد. المفتاح `operator` لا يتغيّر، فلا تتأثر الحسابات القائمة.

| الإجراء | `admin` | `manager` | `operator` | `viewer` |
| :--- | :---: | :---: | :---: | :---: |
| الاطلاع والبحث والطباعة والتصدير | ✅ | ✅ | ✅ | ✅ |

| حذف موظف من الملاك | ✅ | ✅ مع تدقيق | ❌ | ❌ |
| فك قفل الجلسات 🔓 | ✅ | ✅ | ❌ | ❌ |
| الاطلاع على الأرشيف وتنزيل لقطة | ✅ | ✅ | ❌ | ❌ |

## 5. الإنفاذ على الخادم (قواعد Firebase)

```json
{
  "rules": {
    "system_bundle": {
      ".read": true,
      ".write": "auth != null && root.child('roles').child(auth.uid).exists() && root.child('roles').child(auth.uid).child('role').val() !== 'viewer'"
    },
    "active_sessions": {
      ".read": true,
      ".write": "auth != null && root.child('roles').child(auth.uid).exists()"
    },
    "backups_history": {
      ".read": "auth != null && (root.child('roles').child(auth.uid).child('role').val() === 'admin' || root.child('roles').child(auth.uid).child('role').val() === 'manager')",
      ".write": "auth != null && root.child('roles').child(auth.uid).exists() && root.child('roles').child(auth.uid).child('role').val() !== 'viewer'"
    },
    "roles": {
      ".read": "auth != null",
      ".write": "auth != null && root.child('roles').child(auth.uid).child('role').val() === 'admin'"
    },
    "audit_log": {
      ".read": "auth != null && root.child('roles').child(auth.uid).child('role').val() === 'admin'",
      ".indexOn": "timestamp",
      "$entryId": {
        ".write": "!data.exists() && newData.exists() && auth != null && root.child('roles').child(auth.uid).exists() && root.child('roles').child(auth.uid).child('role').val() !== 'viewer'"
      }
    }
  }
}
```

### 5.1 سجل التدقيق إضافة فقط (Append-Only)

الشرط `!data.exists() && newData.exists()` على `$entryId` يسمح بإنشاء قيد جديد فقط:

* تعديل قيد قائم مرفوض، لأن `data.exists()` يكون صحيحاً.
* حذف قيد مرفوض، لأن `newData.exists()` يكون خاطئاً.
* لا يوجد `.write` على `audit_log` نفسه، وهذا مقصود: منح الكتابة على الأب في Realtime Database يورّثها للأبناء ولا يستطيع شرط الابن سحبها.

النتيجة أن السجل غير قابل للمحو **من أي حساب، بما فيه حساب المدير**. هذا ما يجعله دليلاً يُعتد به، ويطابق ما تشترطه ISO 27001 و SOX من عدم قابلية سجلات التدقيق للتعديل.

### 5.2 حدود الإنفاذ المعترف بها

* **الصلاحيات المفصّلة لكل تبويب (`operator`) تبقى في الواجهة.** البيانات كلها كتلة JSON واحدة تحت `system_bundle`، فلا يستطيع الخادم التمييز بين تعديل الموقف اليومي وتعديل الملاك. هذا قيد قائم منذ التصميم الأول ولا يزيده هذا التغيير سوءاً. إصلاحه يتطلب تقسيم `system_bundle` إلى عقد مستقلة — مشروع منفصل خارج هذا النطاق.
* **حجب الاستعادة عن `manager` واجهي بالضرورة.** الاستعادة تقنياً هي قراءة من `backups_history` وكتابة على `system_bundle`، وكلاهما مسموح للإداري. لا يمكن للخادم التمييز بين كتابة عادية وكتابة استعادة ما دامت الحمولة من نفس الشكل.

## 6. حماية آخر حساب مدير

بعد نقل الأدوار إلى `roles/{uid}`، صار حذف سجل المدير الوحيد أو تنزيل رتبته يقفل إدارة الحسابات نهائياً: لا أحد يستطيع منح دور لأحد، ولا مخرج إلا التدخل اليدوي من لوحة Firebase.

**الحل:** يمنع النظام حذف حساب دوره `admin` أو تغيير دوره إلى غير `admin` إذا كان آخر حساب مدير نشط في القائمة، مع رسالة تشرح السبب.

الحماية في الواجهة لا على الخادم، لأن قاعدة Firebase لا تستطيع عدّ الأدمنّين الباقين ضمن تقييم كتابة واحدة بشكل موثوق. وهي كافية عملياً: لا سبيل لبلوغ هذه الحالة إلا عبر النافذة نفسها.

## 7. إظهار فشل المزامنة

### 7.1 المشكلة

`pushDataToCloud` يعالج النجاح وحده:

```js
const res = await cloudFetch(FIREBASE_DB_URL, { ... });
if (res.ok) {
    setCloudSyncStatus({ connected: true, syncing: false, lastSync: ... });
    logAuditEvent('save_system_bundle', currentUserName);
}
// لا يوجد فرع else
```

فإذا رفض الخادم الكتابة لا يحدث شيء: تبقى `syncing` صحيحة إلى الأبد، ولا رسالة، ويظن المستخدم أن عمله محفوظ. والـ `catch` الخارجي يكتفي بـ `console.warn` غير المرئي.

الاحتمال ازداد بعد إحكام القواعد: توكن منتهٍ تعذّر تجديده، أو حساب بلا سجل في `roles`، أو دور `viewer`، كلها ترجع `401`/`403` صامتاً اليوم.

### 7.2 الحل

* إضافة فرع `else` يضبط حالة فشل صريحة تحمل رمز الاستجابة، ويضبط `syncing: false` حتى لا يعلق المؤشر.
* توسيع `cloudSyncStatus` بحقل `error` يعرضه مؤشر المزامنة في الترويسة بلون تحذيري ونص يوضّح أن آخر حفظ لم يصل.
* عند `401` تحديداً: تُعتبر الجلسة منتهية، فيُطلب تسجيل الدخول من جديد بدل ترك المستخدم يعمل على نسخة لا تُحفظ.
* الـ `catch` يضبط نفس حالة الفشل بدل `console.warn` وحده.
* كتابة اللقطة اليومية إلى `backups_history` تحتفظ بـ `.catch` صامت **عن قصد**: فشلها لا يعني ضياع بيانات، إذ نجحت الكتابة الأساسية على `system_bundle` بالفعل، وإزعاج المستخدم برسالة عنها ضرر بلا فائدة. يُكتفى بتسجيلها في `console`.

## 10. التحقق

لا يوجد مشغّل اختبارات في المشروع؛ التحقق يدوي كما هو متبع:

1. تصريف كتلة JSX في الملفات الثلاثة عبر Babel محلياً — صفر أخطاء.
2. تطابق `index.html` مع النسخة السحابية بايت ببايت.
3. `curl` بلا مصادقة على العقد الخمس: الكتابة مرفوضة، وقراءة `roles` و `audit_log` و `backups_history` تُرجع `401`، وقراءة `system_bundle` تُرجع `200`.
4. محاولة تعديل قيد قائم في `audit_log` بتوكن مدير: مرفوضة. ومحاولة حذفه: مرفوضة. وإنشاء قيد جديد: ينجح.
5. دخول بحساب `manager` والتأكد من: ظهور زر فك القفل، وفتح الأرشيف بلا زر استعادة، وغياب زر إدارة الحسابات، وحجب F12، ونجاح تعديل كل التبويبات.
6. محاولة تنزيل رتبة آخر أدمن: مرفوضة برسالة.
7. قطع الاتصال أثناء الحفظ والتأكد من ظهور حالة فشل صريحة بدل بقاء «جارٍ المزامنة».
