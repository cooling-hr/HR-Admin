# دمج مصدر النسختين في جسم واحد — وثيقة تصميم

**التاريخ:** 2026-09-23
**المرحلة:** 2ب من إعادة الهيكلة (تكملة `2026-09-21-professional-restructure-design.md`)
**الحالة:** مقترحة — لم يُنفَّذ منها شيء بعد.

---

## 1. المشكلة

`app/src/editions/offline/App.jsx` و`app/src/editions/cloud/App.jsx` ملفان منفصلان،
11,284 و11,800 سطراً. وقياس الفرق بينهما فعلياً:

| القياس | القيمة |
|---|---|
| مواضع الاختلاف | 61 |
| مجموع الأسطر المختلفة | 866 |
| نسبة التطابق | **96.2%** |

أي أن ~11,100 سطر مكتوب مرتين. وأثر ذلك ليس جمالياً: **كل إصلاح عطل يجب أن
يُكتب مرتين بيدٍ واحدة**، ونسيان إحداهما يعني عطلاً يُصلَح في نسخة ويبقى حياً في
الأخرى بصمت. القاعدة القائمة في `CLAUDE.md` («كل تعديل يُطبَّق على الاثنتين
بتعديل مطابق») اعترافٌ بالمشكلة لا حلٌّ لها: هي تُحمّل الانضباط البشري ما يجب أن
تضمنه البنية.

**الهدف:** مصدر واحد للمنطق المشترك، وملفان ناتجان منفصلان كما هما تماماً.

---

## 2. ما لا يتغيّر

هذه المرحلة **نقل بنيوي بحت**. لا ميزة جديدة، ولا تغيير سلوك، ولا تغيير شكل، ولا
تغيير في صيغة البيانات أو النسخ الاحتياطية.

| | قبل | بعد |
|---|---|---|
| الملفات الناتجة | `hr-offline.html` + `hr-cloud.html` | **نفسهما، منفصلين** |
| إشارات Firebase في الأوفلاين | صفر (فحص آلي) | **صفر، بنفس الفحص** |
| ما يراه الموظف | — | **لا شيء يتغيّر** |
| تقسيم الشاشات إلى `features/` | لم يبدأ | **لا يبدأ هنا** (مرحلة لاحقة مستقلة) |

---

## 3. القيد الحاكم: العزل بالبنية لا بالشرط

عزل نسخة الأوفلاين مضمون اليوم **بشجرة الاستيراد**: `offline/App.jsx` لا يستورد
شيئاً من `data/cloud/`، فلا تدخل شيفرة Firebase حزمتها أصلاً.

**لذلك يُرفض الحل البديهي** — ملف واحد شامل يستورد مصدرَي البيانات ويختار بينهما
بشرط وقت التشغيل:

```js
// مرفوض: يُدخل Firebase في حزمة الأوفلاين رغم أنه لن يُستدعى
import { useCloudDataLayer } from '../data/cloud/useCloudDataLayer.js';
import { useOfflineDataLayer } from '../data/offline/useOfflineDataLayer.js';
const data = edition === 'cloud' ? useCloudDataLayer(args) : useOfflineDataLayer(args);
```

المُجمِّع لا يحذف استيراداً ثابتاً بناءً على شرط وقت تشغيل. النتيجة: حزمة أوفلاين
تحمل Firebase، وفحص العزل يفشل — أو أسوأ، يمرّ بينما الشيفرة موجودة فعلاً.

**القاعدة الملزِمة للتصميم كله:** الملف المشترك **لا يستورد أي طبقة بيانات**. كل
نسخة تستورد طبقتها في ملف دخولها وحده.

## 4. البنية المستهدفة

```
app/src/
  app/
    StaffSystem.jsx          الجسم المشترك (~10,700 سطر) — لا يستورد أي طبقة بيانات
  editions/
    offline/
      App.jsx                مدخل رفيع: يستورد useOfflineDataLayer ويُركّب StaffSystem
      AuthViews.jsx          شاشة الدخول بالرمز وواجهات الحسابات المحلية
    cloud/
      App.jsx                مدخل رفيع: يستورد useCloudDataLayer ويُركّب StaffSystem
      AuthViews.jsx          شاشة الدخول بالبريد، الرمز الرباعي، تولّي الجلسة، نافذة المزامنة
```

شجرة الاستيراد تبقى منفصلة تماماً عند الجذر، فيبقى العزل مضموناً بالبنية كما هو
اليوم بالضبط.

## 5. تمرير طبقة البيانات: الـhook كـprop

الـhook يُستدعى اليوم بـ~25 وسيطاً كلها حالات مُصرَّحة **داخل** الجسم نفسه
(`staff`, `setStaff`, `anchorDate`, `dailyStatusOverrides` …). لذا **لا يمكن**
للمدخل الرفيع أن يستدعيه ويمرّر نتيجته: الوسائط غير موجودة عنده.

الحل: يستقبل الجسم المشترك **دالة الـhook نفسها** كـprop، ويستدعيها في موضعها الحالي:

```jsx
// editions/offline/App.jsx
import { useOfflineDataLayer } from '../../data/offline/useOfflineDataLayer.js';
import { StaffSystem } from '../../app/StaffSystem.jsx';
import { LoginScreen, UserAdminViews } from './AuthViews.jsx';

export default function App() {
    return <StaffSystem edition="offline" useDataLayer={useOfflineDataLayer}
                        LoginScreen={LoginScreen} UserAdminViews={UserAdminViews} />;
}

// app/StaffSystem.jsx
export function StaffSystem({ edition, useDataLayer, LoginScreen, UserAdminViews }) {
    // ... الحالات كما هي حرفياً ...
    const { canEdit, currentUserRole, handleLogin, /* ... */ } = useDataLayer({ staff, setStaff, /* ... */ });
```

**قيد إلزامي:** `useDataLayer` يجب أن تكون دالة ثابتة على مستوى الوحدة
(module-level)، لا دالة تُنشأ داخل الرسم. تغيّر هويتها بين رسمتين يخلّ بترتيب
استدعاء الـhooks في React. المدخلان يمرّران دالة مستوردة، فالشرط محقّق بطبيعته —
لكنه يُذكر هنا لأنه غير ظاهر في الكود.

**ملاحظة نوع:** الـhookان يُعيدان مجموعتين متداخلتين لا متطابقتين (السحابي وحده
فيه `cloudSyncStatus` و`pendingTakeover`؛ والأوفلاين وحده فيه `isAdminPin`
و`revealedPinUsers`). التفكيك في الجسم المشترك يأخذ **اتحاد** المجموعتين، وما لا
تُعيده نسخةٌ يكون `undefined` فيها ولا يُقرأ إلا داخل فرعها. هذا مقبول في `.jsx`
غير المُنمَّط؛ ولو نُمِّط الملف لاحقاً فالنوع اتحادٌ صريح لا تقاطع.

## 6. معالجة الفروق الـ61 — مستويان

التوزيع مقيس لا مقدَّر:

| الفئة | العدد | الأسطر | المعالجة |
|---|---|---|---|
| كتل كبيرة | 12 | ~570 | مكوّن مستقل لكل نسخة، يُمرَّر كـprop |
| مواضع متوسطة | 8 | ~176 | مكوّن أو شرط، حسب التماسك |
| مواضع صغيرة (≤6 أسطر) | 41 | ~120 | شرط `edition` مباشر في الجسم |

**الكتل الكبيرة** كلها دخول ومزامنة وإدارة حسابات: شاشة الرمز الرباعي (172 سطراً)،
نافذة المزامنة (109)، نموذج الدخول (64)، نموذج المستخدم (50)، قائمة المستخدم (34)،
شارة حالة المزامنة (32)، كشف الرموز (31)، شاشة الترحيب (29). تُستخرج كل واحدة إلى
`AuthViews.jsx` الخاص بنسختها.

هذه الكتل موجودة اليوم في نسخة واحدة فقط (السحابية غالباً) وليست في الأخرى، فاستخراجها
**لا يُخرج شيئاً من حزمة الأوفلاين ولا يُدخل فيها شيئاً** — العزل يبقى كما هو تماماً.
الغاية من إخراجها أن يبقى الجسم المشترك مشتركاً حقاً: لو تُركت داخله لاحتاجت شرطاً
يلفّ 172 سطراً، ولدخلت حزمة النسخة التي لا تستعملها بلا داعٍ.

**المواضع الصغيرة** نصوص وأزرار وحقول حالة، بلا أي سلسلة حسّاسة
(`firebaseio`/`identitytoolkit`/`AIza` توجد في طبقة البيانات وحدها، لا في الواجهة).
شرط `edition === 'cloud'` فيها آمن على فحص العزل، وإخراجها إلى مكوّنات يُعقّد أكثر
مما يُبسّط.

## 7. خطة التحقق

النقل حرفي، فالفحص الأقوى هو **المقارنة الآلية للناتج**:

1. تُبنى النسختان **قبل** البدء ويُحفظ الناتجان مرجعاً.
2. بعد كل مهمة تُبنى النسختان ويُقارَن الناتج بالمرجع.
3. أي فرق سلوكي حقيقي يظهر كفرق في الملف المبني؛ والفروق المتوقعة وحدها
   (إعادة ترتيب، أسماء دوال) تُراجَع بالعين وتُوثَّق.

يُضاف إليها بالترتيب:

| البوابة | ما تكشفه |
|---|---|
| `npm run typecheck` | الحقول والمراجع المفقودة |
| `npm run build` | أخطاء البناء والتجميع |
| `check-shell.mjs` | **العزل** — صفر إشارات Firebase في الأوفلاين |
| مراجعة Codex | مرجع تحرّك خارج قائمة الـprops بلا أن يظهر فيها |
| تجربة المستخدم على سطح المكتب | السلوك الفعلي في متصفح حقيقي |

**لا رفع قبل أن يجرّب المستخدم النسختين بنفسه** ويوافق صراحةً.

## 8. المخاطر وضبطها

| الخطر | الضبط |
|---|---|
| مرجع يبقى في الجسم المشترك وهو معرَّف في نسخة واحدة | `typecheck` + البناء + مراجعة Codex؛ والمقارنة الآلية تكشف الأثر |
| كسر العزل | العزل بشجرة الاستيراد لا بالشرط (القسم 3) + الفحص الآلي في كل بناء |
| خلل ترتيب تصريح (TDZ) عند نقل الكتل | الحفاظ على الترتيب النصّي للكتل كما هو؛ لا يُعاد ترتيب تصريح إلا لضرورة موثَّقة |
| ملف مشترك ضخم (~10,700 سطر) | مقبول عمداً في هذه المرحلة: تقسيمه إلى `features/` مرحلة مستقلة، وخلطها هنا يجمع خطرين في خطوة |
| انقطاع العمل في منتصف المرحلة | كل مهمة تنتهي بالتزام وبناء ناجح؛ التوقف بعد أي مهمة يترك النظام عاملاً |

## 9. خارج النطاق

- تقسيم الجسم المشترك إلى `features/` (مرحلة لاحقة مستقلة).
- استخراج مكوّنات `ui/` المشتركة (المرحلة 3 في التصميم الأصلي).
- أي تغيير في الوضع الليلي، أو المكتبات الثقيلة، أو آلية النشر.
- تنميط `StaffSystem.jsx` بـTypeScript.

## 10. قرارات مفتوحة

1. **اسم الجسم المشترك وموضعه:** `app/src/app/StaffSystem.jsx` مقترح لموافقته
   التصميم الأصلي. البديل `app/src/StaffSystem.jsx`.
2. **حدّ «الكتلة الكبيرة»:** الحدّ المقترح ~20 سطراً — ما فوقه مكوّن مستقل، وما
   دونه شرط. المواضع الثمانية المتوسطة تُحسم واحداً واحداً عند التنفيذ.
3. **الوسائط المتوقَّعة من `AuthViews`:** تُحدَّد عند استخراج أول كتلة، ثم تُثبَّت
   لبقيتها.
