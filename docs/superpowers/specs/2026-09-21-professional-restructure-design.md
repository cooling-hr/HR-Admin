# الانتقال إلى هيكلية احترافية (Vite + TypeScript) — تصميم

**التاريخ:** 2026-09-21 · **الحالة:** بانتظار مراجعة المستخدم · **المسار:** معماري

## الهدف

نقل «نظام إدارة الملاك» من ملف HTML واحد (15,288 سطراً، 1.3 ميغابايت، Babel داخل المتصفح) إلى مشروع منظَّم بأداة بناء، **بالسلوك والبيانات نفسها تماماً**، بحيث:
- تُبنى النسختان (سحابية وأوفلاين) من مصدر واحد فينتهي الترحيل اليدوي.
- تُكشف أخطاء التصريح والحقول الخاطئة عند البناء لا عند المستخدم.
- يصير تعديل شاشة مستقلاً عن غيرها.
- يُدمَج نظام الدورات لاحقاً في الهيكل الجديد (انظر «الترتيب»).

## قرارات المستخدم المثبَّتة (لا يُعاد سؤالها)

1. **انتقال تدريجي**، لا إعادة بناء من الصفر. النظام الحي يبقى شغالاً.
2. **الأوفلاين أولاً**؛ السحابية تُبنى بعد إقراره.
3. النسخة الأوفلاين تبقى **ملف HTML واحداً يُفتح بنقرة مزدوجة** (`file://`).
4. **الترتيب:** المراحل 0 و1 و2، ثم دمج نظام الدورات، ثم بقية الشاشات.
5. الرفع (`git push`) بموافقة صريحة فقط؛ الاختبارات الآلية تبقى موقوفة، وبوابة الجودة الجديدة الوحيدة هي `tsc`.

## قيود لا تتغير

- لا ميزات جديدة ولا تغيير في الشكل أو صيغة البيانات والنسخ الاحتياطية أثناء النقل.
- React 18 نفسه بلا مكتبة حالة ولا إطار إضافي.
- `localDateStr()` وصيغة `YYYY-MM-DD`، الفترات الثمانية `PERIOD_TYPES` (و`OPEN_ENDED_PERIOD_TYPES`)، وبقاء `emp.status` مع `getActivePeriod`.
- النسخة الأوفلاين: صفر إشارات إلى `firebaseio` و`identitytoolkit` و`AIza`.
- الملفات الحية الحالية لا تُمَسّ قبل إقرار المرحلة 0 على الحاسوب والهاتف.

## المعمارية

مشروع جديد في `app/` داخل المستودع نفسه.

```
app/
  package.json  vite.config.ts  tsconfig.json  tailwind.config.js  index.html
  public/        manifest.json, sw.js, icon*.png, icon.svg
  scripts/       check-isolation.mjs, publish-desktop.py
  src/
    main.tsx
    app/         التنقل وتركيب الشاشات (StaffSystem)
    core/        dates.ts, arabic.ts, storage.ts
    domain/      periods.ts, safety.ts, water.ts, permissions.ts
    data/        provider.ts + cloud/ + offline/
    features/    dashboard, staff, units, morning, evaluation, water, safety, shift, contract, overtime, ...
    ui/          Button, StatusBadge, PageHeader, Segmented, Icon, Modal
    styles/      الوضع الليلي
  dist/          (خارج Git) hr-cloud.html, hr-offline.html
```

**قاعدة الاعتماد (اتجاه واحد):** `core` ← `domain` ← `data` ← `ui` ← `features` ← `app`. لا تستورد طبقة من فوقها. `domain` بلا واجهة ولا شبكة.

**النسختان:** الفرق الوحيد طبقة `data` (Firebase مقابل PIN محلي + localStorage). `vite.config.ts` يحدد بمتغير `VITE_EDITION` أي تنفيذ يدخل البناء؛ تنفيذ Firebase لا يُستورد في بناء الأوفلاين. بعد البناء يفحص `check-isolation.mjs` الملف الناتج ويوقف البناء عند أي إشارة ممنوعة.

**المخرجات:** ملف HTML واحد لكل نسخة عبر `vite-plugin-singlefile`. Tailwind يبقى من CDN في المرحلة 0 (82 سطراً تركّب أصناف `className` بقوالب نصية، والبناء المسبق يفوته ما يُركَّب وقت التشغيل)، ثم يُنقل لوقت البناء كخطوة مستقلة بعد إقرارها. Babel يُزال من المتصفح، فيُلغى مُحمِّل IndexedDB للشيفرة المحوَّلة.

**الأوامر:** `npm run dev` · `typecheck` · `build:offline` · `build:cloud` · `build`.

## المراحل ومعايير القبول

| المرحلة | المحتوى | معيار القبول |
|---|---|---|
| 0 الهيكل | نقل الملف كما هو إلى Vite/TS. بناء الأوفلاين ثم السحابية. النشر وفحص العزل | النظامان مطابقان للحالي على الحاسوب والهاتف؛ فحص العزل ينجح |
| 1 المنطق الصرف | التواريخ، الفترات، حالة التجهيز، الماء، الصلاحيات إلى `core`/`domain` بأنواع | السلوك مطابق؛ `tsc` نظيف |
| 2 طبقة البيانات | الدخول والحفظ والمزامنة خلف `provider` بتنفيذين | الدخول والمزامنة يعملان في النسختين |
| دمج الدورات | `features/courses/` + `domain/grades.ts` + وضع دخول خاص (قرارات مثبتة في `courses-system-integration-design`) | يُصمَّم في مواصفته الخاصة بعد المرحلة 2 |
| 3 المكوّنات | `ui/` المشتركة | الشكل والوضع الليلي مطابقان |
| 4+ الشاشات | شاشة لكل خطوة، الأبسط أولاً | كل شاشة تُنشر وتُجرَّب وحدها |

**نقطة التوقف:** بعد المرحلة 0 تتحقق أهم المكاسب. التقدير الزمني أولي وغير مؤكد: المرحلة 0 جلسة تقريباً، 1 جلسة إلى جلستين، كل شاشة نصف جلسة إلى جلسة.

## النشر

بعد الانتقال: بناء ثم نشر الناتج. الخيار الموصى به GitHub Actions (يتطلب تغيير مصدر Pages مرة واحدة من حساب المستخدم). الموقع الحي الحالي لا يتغير حتى إقرار المرحلة 0. `publish_desktop_copies.py` يُحدَّث ليأخذ الملفين من `dist/` ويرفض النسخ إن اختل العزل.

## المخاطر

- **اختلاف سلوك بعد النقل:** لا تغيير في السلوك أثناء النقل؛ مقارنة كل شاشة بالحالية؛ مراجعة Codex قبل الالتزام.
- **البيانات القادمة من Firebase/الاستيراد:** الأنواع لا تحميها وقت التشغيل؛ يُضاف تحقق عند حدود النظام في المرحلة 2.
- **أخطاء المنطق:** `tsc` لا يكشفها؛ تبقى المراجعة والتجربة الفعلية.
- **الدخول والمزامنة السحابيان:** لا يُتحقَّق منهما على الأوفلاين؛ يُجرَّبان بحساب اختبار قبل أي رفع.

## قرارات مفتوحة

1. طريقة نشر الناتج (GitHub Actions موصى به).
2. المكتبات الثقيلة (Excel/Word): تُحمَّل عند الحاجة أم تُضمَّن — يُحسم بقياس الحجم في المرحلة 0.
3. مصير الملفات القديمة بعد الاكتمال: أرشفة أم حذف.
